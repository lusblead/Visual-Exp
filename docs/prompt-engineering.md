# Prompt 工程与产品语义边界

## 1. Prompt 要解决的不是“画图”，而是“先把当前层讲明白”

这个产品不让模型一次写完整答案，也不让模型一次生成完整知识图谱。模型每次只完成一种有边界的语义任务：

```text
首次提问
→ Pro 生成当前根场景的导读 + 3–6 个一级章节

当前场景可见
→ Pro 在后台依次准备这些直接章节的下一层
→ Flash 按节点批量准备当前层可见名词的短解释

用户进入一个章节
→ 已准备则立即显示
→ 未准备才把该章节提升为前台 Pro 请求

用户单击名词
→ Flash 返回短解释

用户双击名词、点击“深入”或确认选中的句段
→ Pro 返回更完整的深入解释
```

这样做的产品原因是：抽象层次只有在读者先理解“为什么会有这一层”时才有意义。只返回分类标题，会把模型的组织负担转嫁给用户；一次生成全部深层内容，则会增加首屏延迟、成本和错误面。

## 2. 模型与本地程序的职责

模型只负责不可机械推导的语义：

- 直接答案、背景、作用、机制和边界；
- 章节的阅读顺序，以及章节为何出现在当前位置；
- 可解释名词和同层语义关系；
- 对当前内容适合的表现建议。

本地程序负责稳定事实：

- 协议、版本、文档 ID、节点 ID；
- 父子关系、深度、`childIds`、扩展状态；
- 操作 envelope、文档版本和并发校验；
- 内容长度、术语逐字出现、来源能力和公式策略；
- 布局、响应式、动画和交互状态。

因此 Prompt 是可替换的输入适配器，`visual-explanation-document/2` 才是模型与渲染器之间长期稳定的产品内核。更换模型或画布引擎不应改变知识身份与探索路径。

## 3. 四类生成动作

### Create：建立“可理解的第一层”

模型：`deepseek-v4-pro`。

输入只有原始问题。输出是精简草稿，不包含任何 ID 或图操作字段。Prompt 要求：

1. `orientation` 分别给出直接答案、背景、作用、机制和边界；
2. 生成 3–6 个按阅读顺序排列的一级章节，不生成第二层；
3. 每个章节用 `summary` 给结论、用 `whyHere` 说明为什么此时要讲它、用 `detail` 解释机制、例子或边界；
4. 假设读者不认识问题中的第一个技术名词；
5. 数学采用三态策略：明确要求“不要公式”时完全禁止；明确要求公式、证明或推导时允许；默认 `optional` 只允许一个真正有助理解的小公式，并且公式后必须紧跟通俗解释；
6. 没有检索工具时，不伪造论文、网址、统计数字和来源。

本地适配器将草稿确定性组装为正式文档。首屏只包含根节点和一级章节，不包含任何更深节点。

### Expand：只生成一个场景的直接下一层

模型：`deepseek-v4-pro`。

输入是原问题、当前探索路径和所选节点的可信正文。输出只允许：

- 为父场景补充更具体的 `orientation`；
- 生成 3–5 个直接子章节；
- 说明每个子章节的 `whyHere`；
- 描述这些直接子章节之间的同层关系。

模型不能修改兄弟分支，不能生成孙节点，也不能决定 ID、父指针或版本。前台进入和后台下一层准备共用同一套 Expand 语义契约，区别只在调度优先级，不在内容规则。

### Define / Define Batch：短名词解释

模型：`deepseek-v4-flash`，与 Pro 共用同一个 DeepSeek API Key。

单项和批量结果都遵守 `visual-term-explanation/2`。模型草稿只有：

```json
{
  "definition": "它是什么",
  "relevance": "它为什么出现在当前段落中",
  "terms": ["解释中仍值得说明、且逐字出现的名词"]
}
```

批量请求只合并同一个节点、同一个可信上下文中的 1–8 个名词，响应必须与请求名词集合一一对应。每条短解释最多标注 4 个嵌套名词，递归路径最多 4 层。嵌套请求必须携带服务器签发的上下文凭据，防止客户端伪造“已经验证的父解释”。

这里有意区分“解释正文”和“可点击标注”：`definition` 与 `relevance` 是结果本身，必须严格通过长度、公式偏好等校验；`terms` 只是从正文派生的可选交互索引。模型给出的某个嵌套名词若不在正文、重复祖先、规范化重复、换行、过长或超过上限，本地只丢弃该候选，保留仍然有效的正文与其他候选。被丢弃的词不会进入允许列表，因此也不可能被客户端点开。

Flash 适合短、小、频繁的任务；它减少名词点击后的等待，但不承担场景规划。

### Dive：用户明确要求的深入解释

模型：`deepseek-v4-pro`。

输入只能是当前节点或受验证解释中逐字存在的 1–600 字选区。输出遵守 `visual-deep-explanation/1`，分别包含：

- 直接回答；
- 背景；
- 在当前问题中的作用；
- 工作机制；
- 实际边界；
- 最多 8 个正文中逐字出现的可继续解释名词。

深入结果是当前阅读流中的临时解释层，不生成新图节点，不改变文档版本和导航历史。

## 4. 为什么采用“草稿 → 本地组装 → 本地验证”

JSON mode 只能保证模型尝试返回 JSON，不能保证图结构、版本、来源和内容质量正确。若让模型同时填写语义和机械字段，会把两类错误混在一起：

```text
语义错误：没有讲清楚、分类位置不合理、解释循环
机械错误：ID 冲突、父子不一致、版本错误、字段遗漏
```

当前实现把机械字段从 Prompt 中删除。模型草稿通过动作专用 Schema 后，由本地程序组装正式协议，再执行完整图校验、作用域校验、内容密度校验、术语逐字校验、来源安全和数学偏好校验。只有删除后不改变解释语义与可信状态的可选标注可以局部净化；正文、图、来源、签名上下文和数学偏好仍然 fail closed。模型失败不会直接污染已接受文档。

## 5. 预生成不是“提前生成完整图谱”

场景准备严格停在一个语义前沿。处于 A 层时，只准备 A 的直接入口；这些入口内部新出现的入口，必须等用户真正进入对应场景后才进入准备队列。

场景扩展会推进文档版本，因此按当前阅读顺序串行执行，并在接纳结果前核对请求基线与权威文档版本。名词解释不改变文档，可按节点批量请求，但仍保持单个后台批次并允许前台点击抢占。

客户端取消必须传播到 API 路由和上游模型请求。被抢占或页面隐藏的请求不应继续重试、修复或消耗额度；迟到响应也不能覆盖新的场景、返回后的名词栈或新的深入选择。

## 6. 错误恢复

Provider retry 与 content repair 使用独立的一次预算：

```text
网络 / 429 / 可恢复 5xx
→ 完全相同的不可变请求最多重放一次

空内容 / 截断 / JSON 或核心草稿校验失败
→ 原任务 + 有界候选 + 稳定错误类别，最多修复一次

仅可选嵌套名词标注无效
→ 本地逐项净化，不为装饰性字段重做整段解释

鉴权 / 余额 / 参数 / 内容过滤 / 主动取消
→ 立即停止，不重试、不修复
```

第二个候选仍不合格时显式失败，不切换到 demo 冒充真实结果。诊断只记录动作、模型、阶段、耗时、结束原因、响应长度和稳定错误类别，不记录 Key、Prompt、问题、选区或模型正文。

Content Repair 不是笼统地说“请重试”。本地先按失败字段生成安全类别，再附上一条不含用户正文的定向要求：入口数量/形状检查 `children`，关系错误检查 `fromIndex`、`toIndex` 与自连接，内容错误补足 orientation 与 `summary/whyHere/detail`，术语错误只保留正文逐字项，来源错误撤回无依据声明，数学偏好错误恢复原始 `avoid | optional | requested` 模式。`avoid` 删除全部公式；`optional` 最多保留一个真正有帮助、且紧跟通俗解释的小公式；`requested` 才允许按需展开。分类顺序必须先识别关系、来源、数学偏好和具体内容字段，再识别泛化的 child shape；否则“不能连接同一个子节点”会被误报成入口数量问题，或公式错误只得到无法行动的 `semantic_contract_invalid`，第二次生成仍可能重复原错误。

定向修复之后还必须执行一次跨类别回归检查：修复当前类别不能放松原始 Schema、数量、来源和数学模式。真实链路里曾出现“主候选 child shape 不合格，修复候选修好了 shape 却新加了第二个或没有解释的 ReLU 公式”的级联失败；因此修复 Prompt 会再次重复原始三态数学模式，而不是把所有默认问题粗暴地降为“绝不允许公式”。

## 7. 延迟指标

需要同时区分：

- 上游 TTFT：DeepSeek 返回第一个有效内容 token 的时间；
- 可用结果延迟：完整 JSON 返回，并完成本地组装与全部校验后，用户看到可信内容的时间；
- prepared hit：用户进入或点击时命中已经准备好的内容所需时间。

预生成改善的是 prepared hit 和用户感知等待，不会改变模型本身的 TTFT。Create、Expand 和 Dive 的结构化结果在完整校验前不能以“已接受知识”显示。

## 8. 与工程模块的对应关系

| 层 | 模块 | 职责 |
|---|---|---|
| 交互调度 | `components/lineage-studio.tsx` | 前后台优先级、缓存、取消、导航、解释栈 |
| 线性投影 | `components/lineage-stage.tsx` | 把当前语义层投影为自上而下的阅读流 |
| 模型端口 | `lib/model-port.ts` | 隔离 DeepSeek、OpenAI 和 demo |
| DeepSeek 适配器 | `lib/deepseek-model.ts` | 动作 Prompt、JSON 请求、重试、修复、诊断 |
| 草稿契约 | `lib/deepseek-draft-contract.ts` | 把 Create/Expand 草稿组装为正式文档或操作 |
| 名词契约 | `lib/term-explanation.ts` | 单项、批量、递归路径和正文术语约束 |
| 深入契约 | `lib/deep-explanation.ts` | 选区、五段解释、公式偏好和术语约束 |
| 正式协议 | `lib/visual-contract-*.ts` | 稳定知识身份、图结构和运行时验证 |
| 调度策略 | `lib/scene-prefetch-priority.mjs`、`lib/term-prefetch-priority.mjs` | 一个前沿与当前层的有界准备队列 |
| 来源与内容 | `lib/source-safety.ts`、`lib/visual-content-quality.ts` | Prompt 之外的硬信任边界 |

Prompt 工程与项目的关联可以压缩为一句话：模型负责把当前知识讲清楚，协议负责让知识长期稳定，调度负责让下一步及时可用，渲染器负责让用户读得懂。

## 9. 为什么技术名词要保留双语身份

把所有术语一律翻译成中文会损失三个信息：用户在英文文档中能否认出它、能否继续检索、以及它是不是一个已有标准组件。因此 Prompt 只对有公认英文名称、且双语确实有助识别的技术组件要求首次出现时使用双语，例如：

```text
Encoder（编码器）
Decoder（解码器）
Feed-Forward Network（前馈网络）
```

普通中文概念不机械添加英文。`terms` 也必须把完整双语写法作为一个字面项，并确保正文逐字出现；不能把 `Encoder` 和 `编码器` 拆成两个相互竞争的点击区域。本地边界匹配器仍负责最终验收。

## 10. Prompt 不生成 Mermaid，而是生成可投影的语义

“架构问题需要图”不等于让模型直接输出 Mermaid、UML 源码、SVG 或坐标。那会把模型、DOM、主题和画布引擎重新耦合在一起，也会引入脚本与布局风险。

当前 Prompt 只允许模型给出：

```text
有顺序的直接子节点
同层 relation 的 fromIndex / toIndex / kind / label
语义 view：sequence / timeline / compare / cluster / grid
```

本地适配器把索引组装成 canonical ID，本地 `SemanticDiagram` 再投影成安全的辅助结构图。正文始终保留；没有可靠关系时宁可不画线，也不让渲染器猜测。

## 11. 知识主体不能由模型“背诵”

文学、法规、代码或其他可识别对象的解读，应先让用户看到主体，再看解释。但原文不是 Prompt 的自由生成字段：

```text
用户提供 / 已核验公共领域 / 已授权
→ 可以展示完整主体

受保护作品
→ 只展示必要且有界的摘录

来源不可用或无法核验
→ 明确说明缺失，不从模型记忆重构
```

`lib/primary-material.ts` 在模型之外承担这个边界。这样即使更换 DeepSeek、OpenAI 或未来的网站中继，原文身份、来源和版权状态也不会随模型回答漂移。

## 12. 缓存、可见性和任务必须是三个状态

以前“关闭解释”或“切换到 B”会连带取消 A，是因为界面可见状态被误当成请求生命周期。现在 Prompt 只负责生成内容，调度按稳定内容身份管理任务：

```text
visible：当前是否显示
task：是否正在生成、由哪个 generation 拥有
cache：结果是否已经可复用
```

关闭卡片只改变 `visible`；A 和 B 的 Flash/Pro 任务可独立完成；重新点击 pending 或 ready 的身份不会再次发送 Prompt。只有新根文档、可信正文变化、卸载或有界淘汰才允许使对应缓存失效。这既修正切换节奏，也直接减少重复 Token。

## 13. 网页模型中继与 Prompt 的关系

未来若某个网站 AI 正式允许中继，Visualized Exp 仍在自己的界面中接收问题并构造同一套动作 Prompt。网页只是一种 `GenerationGateway` transport：

```text
Visualized Exp 组装有界 Prompt
→ 授权中继提交一次并关联 jobId
→ 只取回该 jobId 对应的新回答
→ 本地解析、组装、校验
→ 渲染 VisualDocument
```

不会把完整知识图、无关历史或 API Key 发给网页端。`%USERPROFILE%\Documents\Personal-Hub-Android\browser-extension` 可复用页面读取、完成态检测、结构化 blocks、loopback 鉴权和幂等经验，但它目前只是采集器，没有提交 Prompt 与 job-to-answer 关联。ChatGPT 网页自动读回还受现行服务条款限制，当前不能作为可发布后端；接口只为正式授权的提供方保留。
